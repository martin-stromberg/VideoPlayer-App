# Release Notes

## Important Notes Before Update

- QR-/ticket-based onboarding requires a server update (`POST api/pairing/bootstrap` plus `POST api/auth/refresh` and `POST api/auth/logout`): onboarding via the pairing QR code / ticket URL / short code from the server admin UI ("Devices" section) requires a VideoPlayer server release that includes the bootstrap endpoint (server issue #231). On a server without the endpoint the pairing code entry shows a clear notice prompting a server update — manual address entry, one-time-code pairing and the sign-in page keep working unchanged as fallbacks.
- Device pairing requires a server update (`POST api/pairing/exchange`): the app now authenticates each device to the server with a device-bound token obtained through a one-time pairing code created in the server admin UI ("Devices" section). This requires a VideoPlayer server release that includes the pairing endpoint (server issue #228). On a server without the endpoint, a new setup only proceeds if a static API token is configured — otherwise the app shows a notice prompting a server update.
- Static API token no longer the primary mechanism, but still configurable as a transition: existing installations with a configured static token (environment variable `VIDEOWEBPLAYER_MAUI_API_TOKEN`, publish property `VideoPlayerApiToken`, token file `client-api-token.txt`) keep working unchanged; pairing is only requested when neither a device token nor a static key is available.

## What's New

- Download storage reconciliation (`VideoPlayer.Mvu`, issue #51 step 1): the app now reconciles the video storage directory against the download manifest on startup and when opening the Downloads page — leftover partial files of cancelled/failed/interrupted jobs are removed automatically, files without a manifest entry are detected and shown below the quota line ("davon x GB nicht zugeordnet") instead of invisibly consuming storage, and entries marked complete without a file are corrected to a retryable failure. Running transfers and completed downloads are never touched. Coverage: new reconcile service tests plus MVU and contract tests (1350 unit tests).
- Premature end-of-playback events no longer trigger the completion flow (`VideoPlayer.Mvu`, issue #49 step 5): the media element's `MediaEnded` event used to unconditionally mark the title as watched, report the end position and start the next episode/playlist entry when auto-resume is enabled — a spuriously firing event (e.g. on a stream abort, format or position change, or a stale event arriving after the next title was already loaded) falsely completed the current or even the following title mid-playback. The event is now plausibilized against the reported playback state first: it only counts as a real end when the position lies within a fixed tolerance window at the end of the duration (300 seconds, oriented at the "mark as watched" end window), and an unknown/zero duration disqualifies the event outright. Non-plausible events trigger neither the watched marking and end-of-progress report nor the auto-advance, uniformly for series/single playback and playlists; a genuine end runs the unchanged completion flow. Coverage: new unit tests for the mid-playback, unknown-duration, tolerance-boundary, stale-event and playlist cases plus updated fixtures for the existing end tests (1335 unit tests, 11/11 playback E2E tests).
- Continue Watching opens the title detail page with playback on top (`VideoPlayer.Mvu`, issue #49 step 4): tapping a playable entry in the home page's Continue Watching list (movie or episode) used to launch the player immediately, so closing it dropped the user back on the home list and the title's information was unreachable without going through the source browser — matching the server application, the tap now pushes the title's detail page onto the stack and starts playback on top of it, so closing the player returns to the opened detail page. Playlist-bound entries keep their direct playlist start (the playlist order would be lost on a detail page), non-playable entries (show, season, collection) still open the detail page only, and the series context for the next-episode queue keeps loading in the background. Offline the same applies to movies and episodes with a usable series reference, while an episode without it keeps the previous direct playback and non-selectable placeholders stay inert. Coverage: reworked unit tests pinning the effect order (details navigation before player navigation) plus three new offline cases, and reworked end-to-end tests proving the detail request alongside the stream and the return to the detail page after closing the player (1329 unit tests, 6/6 continue-watching E2E tests).
- Source browsing keeps the scroll position when loading more results (`VideoPlayer.Maui` + `VideoPlayer.Mvu`): scrolling to the end of a source's result grid used to jump the list back to the top on every appended page, because the bound `ItemsSource` was replaced wholesale — comfortable browsing was impossible. The page now binds a stable observable list that `SourceItemListSync` reconciles incrementally (shared prefix by item id untouched, appended pages raise only add-notifications at the end), so the view keeps its position and new entries simply appear at the end; first load, genre switches and new searches still show the list from the top, for unfiltered results and search/genre hits alike (same display and paging path). Coverage: new unit tests for the incremental sync plus a new end-to-end test driving the real app through scrolling to the end, two appended pages and a scroll percent above zero afterwards (1326 unit tests, 6/6 source E2E tests).
- Source browsing search field keeps unconfirmed input (`VideoPlayer.Maui`): typing a search term on a source's overview page no longer gets wiped by background model updates (sync, progress, network or loading ticks) — the field is only re-mirrored when the actually submitted search text changes, so an unsubmitted entry survives and stays editable until the search/Return key fires the query, reloading the result list filtered from the first page; the submitted term remains visible as the recognizable active filter when returning to the page, and context resets (source switch, sign-out, session expiry) still clear it. No live search per keystroke — the existing submit-based pattern is unchanged. Coverage: new contract tests pinning the mirror guard and a new end-to-end suite driving the real app through typing across model ticks, Enter-submit with the `search` request and the return-to-page case (1320 unit tests, 61 E2E tests).
- Source browsing genre bar handled correctly (`VideoPlayer.Maui` + `VideoPlayer.Mvu`): the genre chip bar on a source's overview page only appears when the server actually returns genres for that source (`api/SourceGenres/{id}`); an empty server list or a failed genre request no longer leaves a functionless "Alle"-only row — the bar stays hidden while the poster grid keeps loading normally. With genres present, selecting a chip reloads the result list filtered from the first page and "Alle" clears the filter again (existing behavior, unchanged). Coverage: new unit tests pinning the visibility rule (`SourceBrowserState.ShowGenreFilter`) and the empty-server-list fallback, plus two new end-to-end tests driving the real app through the source menu, genre selection with the `genreId` request and the hidden-bar case (1316 unit tests, 58 E2E tests in the affected suites).
- Program log writes activity entries again in the installed app (`VideoPlayer.Maui`): the released app recorded only the marker lines in `videoplayer.log` — every `ILogger`-based breadcrumb (app start, sign-in, playback, downloads, connectivity) was silently discarded because the `MauiAppBuilder` defaults to a null logger factory that ignores DI-registered `ILoggerProvider`s unless `builder.Logging` is configured; `builder.Logging.AddDebug()` had covered this in debug builds only. `MauiProgram` now activates the logging pipeline explicitly (`builder.Services.AddLogging()`), so user actions appear in the log in release builds as intended; a new contract test pins the activation.
- Diagnostic program log content (`VideoPlayer.Maui` + `VideoPlayer.Mvu` + `VideoPlayer.Storage` + `VideoPlayer.ApiClient`): the "Protokollierung" switch now writes a genuinely useful program log instead of only the enable/disable marker — sparse, readable breadcrumbs for app start and storage initialization, server health checks and source switches, sign-in/sign-out and silent re-authentication (status only, never credentials), session expiry, realtime event connection up/down/lost, playback source resolution (media type/id, source kind, resume position), playback start/end/failure with the display title, Picture-in-Picture/mini-player toggles, synchronization results with counters, progress report queueing/discarding/resending, download jobs and state changes, automatic download runs, device token discard/rejection and online/offline changes including the WLAN context. All previous `Debug.WriteLine` diagnostics across the app projects now flow through injected `ILogger` into the file, and the previously unused API-client logger hook is wired so retry/401 warnings land in the log as well. The log stays lean on purpose — no 5-second progress ticks, no per-item or per-image entries, noise-prone paths sit below the information threshold — and it stays safe to share: usernames, passwords and tokens are never logged and any `access_token` value reaching a technical message is masked centrally before it hits `videoplayer.log`. Coverage: new recording-logger test stubs plus unit tests for every new logging path (including no-credentials-in-log and token-masking assertions), contract pins for the remaining zero `Debug.WriteLine` footprint and the connectivity/PiP/playback-failure/logout breadcrumbs, and three new end-to-end tests driving the real app through sign-in and playback proving `[INFO]` entries beyond the marker, logout/PiP sub-flows and a `[ERROR]` playback failure — all without secrets in the file (1280 unit tests, 56 E2E tests).
- iPad: native fullscreen and Picture-in-Picture buttons reachable again (`VideoPlayer.Maui`, issue #45): on iPad the app's player overlays blocked the native `AVPlayerViewController` top bar — the header band's parent layout now carries `InputTransparent` itself (under iOS a layout still hit-tests in its own bounds even with transparent content), and under `#if IOS` both the header band (`OverlayChrome`) and the playlist navigation bar are shifted below the native top bar by the named offset `IosNativeControlsClearance` (96 pt), so the native fullscreen/PiP buttons are neither covered nor blocked while the playlist navigation stays fully operable. iOS Picture-in-Picture continues to run exclusively through the native transport controls (the app's own mini-player button stays hidden on iOS); the Windows layout and behavior are unchanged. - iOS series view fixed — episode list, season order and stable season selection (`VideoPlayer.Maui`, issue #43 step 8): on iOS the series detail page no longer drops its episode list — the virtualized `CollectionView` inside the page's `ScrollView` (which iOS could measure with zero height) was replaced by a `BindableLayout` list following the `MediaCarousel` pattern, with the episode card tap still opening the episode detail page. The season picker now only rebuilds when the season list actually changes and applies `SelectedItem` only on real divergence, and the selection handler ignores echo events that would re-report the already applied model selection — this stops the season order glitch and the snap-back to "Staffel 01" on iOS. Verification boundary: the defect was iOS-specific and no iOS host was available for a runtime check — the cause fixes were verified on Windows (three new end-to-end tests for the series view: visible episode list, ascending season order, season switch that sticks) and the remaining iOS verification is documented.
- Downloads in playlist order for playlist-bound media (`VideoPlayer.Mvu` + `VideoPlayer.Storage`, issue #43 step 7): the automatic download preload now follows the playlist order for Continue Watching entries that carry a playlist reference — instead of enqueueing the next series episodes, the service pages through `api/playlists/{id}/entries/paged` from the current playlist entry and schedules the next preload-count downloadable and accessible entries in the server's playlist order (playlist-bound movies download themselves plus the following playlist entries). The playlist reference (`PlaylistId`/`PlaylistEntryId`/`PlaylistSortOrder`) is persisted on the download manifest via the established column-migration pattern, so existing installs upgrade in place without data loss; entries without a playlist reference keep the series order, and a stale entry reference or an unreachable playlist falls back to the series path. Coverage: new unit tests for the playlist ordering, skipped non-loadable/inaccessible entries, persisted playlist/series hints on the manifest, movie self-plus-next scheduling, both fallback cases and the schema migration (1285 unit tests).
- Playlist administration on the device (`VideoPlayer.Maui` + `VideoPlayer.Mvu` + `VideoPlayer.ApiClient`, issue #43 step 6): playlists can now be managed right in the app — "Neue Playlist" on the overview opens a dialog form (required name with inline validation, description, sort mode), and a new "Verwalten" button on the playlist detail page bundles "Bearbeiten" (name/description), "Playlist löschen" with a confirmation dialog and return to the overview, a sort-mode switch, "Genres bearbeiten" and — for administrators only — "Öffentlich schalten"/"Privat schalten", all through the server administration endpoints. Entry management completes the story: "Zu Playlist" on the media detail page adds the media item to one of your own playlists (with the server's notice for duplicates), and a per-entry context menu removes it or — in manual sort mode — moves it to the beginning, to the end (via max-sort-order + 1) or one position forward/backward, with edge actions hidden. Conflict handling mirrors the server contract: removing an entry tied to Continue Watching asks "Aus Weiterschauen entfernen?" and only the confirmed retry carries `confirmContinueWatchingRemoval=true`, while switching away from manual sort order asks "Sortiermodus ändern?" and retries with `confirmLossOfManualOrder=true` — cancelling either dialog leaves everything untouched. A genre editor lists all server genres as selectable chips preselected from the playlist's genres, with save and reset-to-computed actions; the public/private switch is only offered when the sign-in token carries the `IsAdmin` claim (the server stays authoritative and enforces permissions again), and public playlists owned by other users show no management controls at all. Coverage: new unit tests for every administration endpoint (verb, path, body, confirm flag), service mapping including 409 conflict outcomes, all MVU transitions, plus eleven new end-to-end tests driving the real app through create/edit/delete, add-from-details, entry removal with and without the Continue Watching confirmation, all three move actions, the sort-mode conflict flow, genre set/reset, the admin public switch and the read-only view of a foreign public playlist (1278 unit tests, 50 E2E tests).
- Playlist playback and playlist-aware Continue Watching (`VideoPlayer.Maui` + `VideoPlayer.Mvu` + `VideoPlayer.ApiClient`, issue #43 step 5): playlist entries are now playable — the new "Abspielen" button on the playlist detail page starts playback at the first playable and accessible entry (`POST api/playlists/{id}/play`), and tapping a playable entry starts right at that entry (`entryId`); non-playable entries (shows, seasons, collections, inaccessible media) keep opening the media detail page. During playlist playback the player offers "Zurück"/"Weiter" buttons plus a context line showing the playlist name and position, manual navigation resolves through `play/previous`/`play/next`, and both the end-of-title auto-advance and the error fallback now resolve the next entry through `play/advance` — the ordering always comes from the server, which skips non-playable or inaccessible entries (HTTP 204 ends playback). Continue Watching entries that originated from a playlist carry the playlist reference (`playlistId`/`playlistName`/`playlistEntryId` of the server DTO) through to the home page: tapping them continues playback through the playlist context so the next title follows the playlist order instead of the series order, while entries without a playlist reference keep the existing detail-page-independent series resolution (a media item that is no longer part of the playlist falls back to it as well). The server-supplied `startPositionSeconds` is applied authoritatively, even when the same media exists in another context. Coverage: new unit tests for every MVU transition (start, entry selection, Continue Watching guard with/without reference, navigation guards and exhaustion, auto-advance, error fallback, series-path regression), service tests for the play endpoints (mapping, `entryId`/`currentEntryId` query, 204 handling), mapping tests for the playlist reference and the resume-position override, plus six new end-to-end tests that drive the real app through button start skipping a non-playable entry, entry selection, previous/next navigation, auto-advance, error fallback and a playlist-bound Continue Watching entry that advances by playlist order without a series request (1175 unit tests, 39 E2E tests).
- Playlists overview and detail view (`VideoPlayer.Maui` + `VideoPlayer.Mvu` + `VideoPlayer.ApiClient`, issue #43 step 4): a new "Playlists" menu entry (between Favorites and Downloads) lists the signed-in user's own playlists (`api/playlists`) and all public playlists (`api/playlists/public`) in a single scrollable view with section headers — each card shows the playlist cover (`api/playlists/{id}/cover`, title fallback when none), the sort mode and the display genres. - Page lifecycle leak fixed (`VideoPlayer.Maui`): six pages (Home, Media Details, Downloads, Favorites, Source Overview, Profile) subscribed to the MVU host's `ModelChanged` event in their constructors without ever unsubscribing — closed page instances stayed attached to the host and kept reacting to model changes (memory leak, stale UI updates, potential duplicate reactions). - QR-/ticket-based onboarding (`VideoPlayer.Maui` + `VideoPlayer.Mvu` + `VideoPlayer.ApiClient` + `VideoPlayer.Storage`): first-run setup now completes in a single step — a new "Mit Kopplungscode verbinden" card on the server setup page accepts the ticket URL from the pairing QR code in the server admin UI ("Devices" section) or the 8-character short code, and on iOS/Android a camera scanner page (ZXing.Net.Maui, camera permission declared per platform, first detection wins) reads the QR code directly. Silent renewal now refreshes via `POST api/auth/refresh` first (the rotated refresh token replaces the old one immediately) with the stored-credentials re-login as fallback; signing out revokes the refresh token server-side best-effort via `POST api/auth/logout` and clears all local session secrets. Clear inline errors cover unreadable input, unreachable ticket servers (never persisted), invalid/expired tickets, temporary lockout and servers without the bootstrap endpoint; manual address entry, admin-code pairing and the sign-in page remain available as fallbacks. On Windows there is no camera scan — the manual entry covers it. - Device pairing via one-time code (`VideoPlayer.Maui` + `VideoPlayer.Mvu` + `VideoPlayer.ApiClient` + `VideoPlayer.Storage`): on first start the app pairs the device with the server using a one-time code created in the server admin UI — a new "Pair device" section on the server setup page accepts the code and exchanges it via the public, rate-limited endpoint `POST api/pairing/exchange`. ## Wichtige Hinweise vor dem Update

- QR-/Ticket-Onboarding erfordert ein Server-Update (`POST api/pairing/bootstrap` sowie `POST api/auth/refresh` und `POST api/auth/logout`): Das Onboarding über den Kopplungs-QR-Code / die Ticket-Adresse / den Kurzcode aus der Server-Verwaltung (Bereich „Geräte") setzt ein VideoPlayer-Server-Release mit dem Bootstrap-Endpunkt voraus (Server-Issue #231). Auf einem Server ohne diesen Endpunkt zeigt die Kopplungs-Eingabe einen verständlichen Hinweis auf das Server-Update — Adresseingabe, Einmal-Code-Pairing und Anmeldemaske funktionieren unverändert als Fallback weiter.
- Geräte-Pairing erfordert ein Server-Update (`POST api/pairing/exchange`): Die App authentifiziert jedes Gerät jetzt mit einem gerätegebundenen Token, das über einen Einmal-Pairing-Code aus der Server-Verwaltung (Bereich „Geräte") bezogen wird. Voraussetzung ist ein VideoPlayer-Server-Release mit dem Pairing-Endpunkt (Server-Issue #228). Auf einem Server ohne diesen Endpunkt gelingt eine Neueinrichtung nur mit einem konfigurierten statischen API-Token — andernfalls zeigt die App einen Hinweis mit der Aufforderung zum Server-Update.
- Statischer API-Token nicht mehr der primäre Mechanismus, aber weiter als Übergangslösung konfigurierbar: Bestehende Installationen mit hinterlegtem statischem Token (Umgebungsvariable `VIDEOWEBPLAYER_MAUI_API_TOKEN`, Publish-Eigenschaft `VideoPlayerApiToken`, Token-Datei `client-api-token.txt`) funktionieren unverändert weiter; das Pairing wird nur eingefordert, wenn weder ein Geräte-Token noch ein statischer Schlüssel vorhanden ist.

Eine neue Anmeldemaske fragt nur Benutzername und Passwort ab (Benutzername vorbefüllt), zeigt Inline-Fehler und bietet den Weg zurück zur Serverauswahl. Abgelaufene Anmelde-Tokens werden im Hintergrund über eine erneute Anmeldung mit den gespeicherten Zugangsdaten erneuert; nur fehlende oder abgelehnte Zugangsdaten führen zur Anmeldemaske. Nach einer Backup-Wiederherstellung verbindet sich die App automatisch mit dem letzten Server — die erneute Passwortabfrage erfolgt nur, weil Geheimnisse bewusst nicht ins Backup gelangen.
- Netzwerkstatus-Erkennung und Synchronisation: Die App erkennt Online↔Offline-Wechsel zur Laufzeit, zeigt den Offline-Hinweis ohne die aktuelle Seite zu verlassen und stellt die Verbindung nach Netzwerk-Wiederkehr automatisch wieder her (Erreichbarkeitsprüfung, stille Anmeldung). Eine SignalR-Echtzeit-Verbindung zum Server-Hub `hubs/mediaupdate` aktualisiert Weiterschauen, Favoriten und neu eingescannte Inhalte ohne manuelle Aktualisierung; bei endgültigem Verbindungsverlust wird sie im Online-Zustand neu aufgebaut. Nicht zustellbare Wiedergabefortschritte landen in einer persistenten, backup-pflichtigen Warteschlange (`pending_progress`) und werden bei der Synchronisation in chronologischer Reihenfolge nachgesendet — je Medium nur der neueste Stand, gelöscht erst nach erfolgreicher Übertragung — und überstehen App-Neustarts und Backup-Wiederherstellungen.
- Startseite mit gecachten Medienlisten (`VideoPlayer.Maui` + `VideoPlayer.Mvu`): Die neue Startseite zeigt drei horizontale Listen — „Weiterschauen", „Favoriten" und „Neu im Programm" — als Poster-Karten im Stil der bisherigen App. Die Listen werden zuerst aus dem lokalen Cache geladen, sodass beim erneuten Öffnen sofort Inhalte sichtbar sind (auch offline); sobald aktuelle Serverdaten vorliegen oder ein Server-Ereignis (Fortschritt, Favoriten, neu eingescannte Inhalte) den zugehörigen Cache aktualisiert, frischen sich die Listen automatisch auf. Vorschaubilder kommen über `api/pictures/{id}` und liegen in der nicht backup-pflichtigen Vorschau-Ablage. Das Antippen eines Eintrags öffnet über die Route `mediadetails` die Detailseite des Mediums.
- Hero-Kopfbereich der Startseite (`VideoPlayer.Maui` + `VideoPlayer.Mvu`): Oberhalb der Medienlisten zeigt die Startseite einen vollbreiten Kopfbereich nach Web-Vorbild — das servergenerierte Hintergrundbild (`api/pictures/hero-background`, Bearer-authentifiziert) in Cover-Darstellung unter geschichteten Dunkelgradienten mit Kicker-Chip, Servernamen als Titel und Beschreibungstext; die Höhe folgt der Fensterbreite (mindestens 260, höchstens 520). Das Bild wird nur flüchtig gehalten (keine Dateiablage); ohne Bild bleibt der Bereich mit Gradienten und Texten stabil. Über die neue, positiv formulierte Einstellung „Kopfbereich anzeigen" (Abschnitt „Darstellung", Standard: aktiviert) lässt sich der Bereich dauerhaft ein- und ausblenden — die Einstellung bleibt nach dem Neustart erhalten und wird nicht zum Server synchronisiert.
- Quellen-Browsing und Medien-Detailseiten: Die Menüseite „Quellen" listet die vom Server freigegebenen Medienbereiche (mit Icons, klarem Offline-Hinweis ohne Verbindung und „Erneut laden" bei Fehlern). Die Auswahl öffnet eine Browsing-Seite mit horizontaler Genre-Leiste (inklusive „Alle"), Textsuche und Poster-Raster mit seitenweisem Nachladen. Detailseiten decken Filme und Episoden (Basisdetails), Filmkollektionen (enthaltene Filme) und Serien (Staffel-Auswahl mit Episodenlisten) ab; Episoden und Staffeln lösen über eingebettete Bezüge zum Serienkontext auf. Ein Favoriten-Stern schaltet die Markierung serverseitig um (`api/favorites/toggle`), erneuert die lokale Kopie `cached_favorites` autoritativ und aktualisiert die Startseiten-Favoriten automatisch — kein stilles Umschalten, konsistent nach App-Neustart.
- Favoriten- und Profil-Seite: Die Menüseite „Favoriten" zeigt die Favoriten des am Server angemeldeten Benutzers als Poster-Karten mit Titel und Medientyp im Stil der Webanwendung. Online bleibt der Server führend — die lokale Kopie `cached_favorites` wird zuerst synchronisiert und dann angezeigt; die Aktion „Entfernen" je Eintrag löscht den Favoriten serverseitig (`api/favorites/remove` mit der Favoriten-Eintrags-ID), erneuert die Kopie und die Startseiten-Favoriten folgen automatisch. Offline bleibt die gespeicherte Liste mit klarem Hinweis sichtbar und das Entfernen ist gesperrt. Ein Tap auf eine Karte öffnet die Detailseite des Mediums mit dem Serienkontext (Staffel/Episode). Die Profil-Seite zeigt den angemeldeten Benutzer (Benutzername und, soweit im Token enthalten, E-Mail), das aktive lokale Profil (`VIDEOPLAYER_PROFILE`) und die Serveradresse; „Abmelden" beendet die Sitzung lokal ohne Server-Endpunkt — Token und Zugangsdaten werden gelöscht und die App kehrt zur Anmeldemaske zurück, während Serverliste, Einstellungen und Offline-Daten erhalten bleiben.
- Videowiedergabe mit Picture-in-Picture und Fortschrittsverfolgung (`VideoPlayer.Maui` + `VideoPlayer.Mvu` + `CommunityToolkit.Maui.MediaElement` 10.0.0): Eine eigene Wiedergabeseite (Route `player`) spielt Server-Streams (`api/items/{typ}/{id}/stream` mit Zugriffstoken) oder fertige Downloads aus dem lokalen Manifest ab — die Quellenabstraktion ist für den kommenden Download-Ausbau vorbereitet. Die Wiedergabe setzt am gemerkten Weiterschauen-Stand fort (Serverliste, offline aus der Cache-Kopie). Der Fortschritt wird im Fünf-Sekunden-Takt gemeldet, innerhalb des eingestellten Endfensters als „angesehen" markiert und offline verlustfrei in `pending_progress` vorgehalten — bei Online-Rückkehr wird automatisch nachgesendet. Bei aktivierter Auto-Fortsetzung startet gegen Ende automatisch die nächste Episode (staffelübergreifend, in Episodenreihenfolge) — nie im Pausenzustand. Quell- oder Abspielfehler zeigen eine verständliche Meldung und fallen auf die nächste Episode zurück, sofern vorhanden. Unter Windows schaltet ein „Mini-Player"-Schalter das App-Fenster in ein kompaktes, immer vordergrundiges Overlay; unter iOS stellt die native Transportsteuerung Picture-in-Picture bereit (Hintergrund-Audio ist in der `Info.plist` deklariert). „Abspielen"-Schaltflächen stehen auf der Detailseite für Filme und Episoden sowie an jedem Eintrag der Episodenliste.
- iOS-Deployment-Skript gehärtet (`scripts/iOS-Deployment.ps1`): Der Store-/Release-Build schlägt nicht mehr mit dem kryptischen `MSB1006` fehl, wenn ein Eigenschaftswert (z. B. `VideoPlayerApiToken`) ein Anführungszeichen, eine Raute oder einen Zeilenumbruch enthält — das Skript trimmt Werte jetzt und bricht frühzeitig mit einer verständlichen Meldung ab, die Eigenschaft, Zeichenart und Position nennt und die Response-Datei-Zeile maskiert zeigt (Secrets bleiben `***`). Schlägt der `dotnet`-Aufruf fehl, gibt das Skript die Response-Datei-Inhalte zur Diagnose maskiert aus.
- Downloads-Seite ohne Flackern (`VideoPlayer.Maui` + `VideoPlayer.Mvu`): Die Downloads-Liste wird bei jedem Fortschritts-Tick nicht mehr komplett neu aufgebaut — eine stabile, beobachtbare Liste aus Eintrags-ViewModels wird in-place abgeglichen, sodass sich bei laufendem oder geplantem Download nur der Fortschrittsbalken des betroffenen Eintrags verändert und die übrige Anzeige unberührt bleibt. Laden, Einreihen, Abbrechen, Löschen, Fortsetzen und automatische Downloads bleiben unverändert.
- Download-Verwaltung und automatische Downloads (`VideoPlayer.Mvu` + `VideoPlayer.Maui`): Medien lassen sich über „Herunterladen" auf der Detailseite (Film-Kopfbereich und je Episode) für die Offline-Nutzung laden. Die Menüseite „Downloads" zeigt alle Aufträge mit Titel, Typ, Zustand, Fortschrittsbalken und verständlichen Fehlern — offline nutzbar, da der Bestand im lokalen Manifest (`download_manifest`, außerhalb des Backups) liegt — samt den Aktionen Abbrechen, Erneut versuchen und Löschen sowie der Kontingent-Belegung. Bis zu zwei Downloads laufen parallel; unterbrochene Aufträge werden beim Verbindungsaufbau, nach App-Neustart und bei Netzwerk-/WLAN-Rückkehr automatisch neu gestartet (kein Range-Resume, der Server-Stream beginnt erneut). Das konfigurierte Speicherplatzkontingent (Standard 5 GB) wird vor und während der Übertragung durchgesetzt — auch über parallele Transfers hinweg. „Downloads nur im WLAN" hält Aufträge bis zu einer ungedrosselten Festnetz-Verbindung zurück (WLAN oder Ethernet). Bei aktivierten automatischen Downloads lädt die App die nächsten Episoden der Weiterschauen-Einträge vor (Anzahl aus der Einstellung, staffelübergreifend im Serienkontext; Film-Einträge laden den Film selbst), gedrosselt nach Synchronisation, Listen-Änderung und Einschalten der Einstellung; optional werden Downloads gesehener Episoden automatisch entfernt. Die Wiedergabe bevorzugt die lokale Datei und fällt bei fehlender Datei auf den Server-Stream zurück.
- Vollständiger Offlinebetrieb und Wiederherstellung nach Backup (`VideoPlayer.Mvu` + `VideoPlayer.Maui` + `VideoPlayer.Storage`): Ohne Serververbindung bleibt die Startseite nutzbar — „Weiterschauen" wird ausschließlich aus abgeschlossenen Downloads mit vorhandener Datei gebildet, fehlende Folge-Episoden erscheinen als abgedunkelte Platzhalter-Karten mit dem Hinweis „Nicht heruntergeladen", Favoriten und „Neu im Programm" zeigen den letzten Cache-Stand. Downloads spielen aus der lokalen Datei; Detailseiten entstehen als Offline-Snapshots, die serverseitige Aktionen (Favorit, Download, Quellen, Profilabruf) unterbinden. Nach einer Cloud-Backup-Wiederherstellung nutzt die App den zuletzt verbundenen Server sowie gespeichertes Token oder Zugangsdaten; fehlende Geheimnisse führen zu einem verständlichen Wiederanmelde-Hinweis auf der Anmeldemaske mit vorbefülltem Benutzernamen. Ist der bekannte Server nicht erreichbar, wechselt die App bei lokalem Datenbestand in den Offline-Modus, sonst in die Server-Einrichtung. Bei Wiederverbindung läuft eine Voll-Synchronisation, die ausstehende Fortschritte nachsendet und die Startseiten-Listen aktualisiert. Beschädigte Cache-Einträge werden verworfen und neu synchronisiert; beschädigte Datenbankdateien werden als `*.corrupt-*` beiseitegelegt und neu aufgebaut — ein Hinweisbanner informiert den Nutzer.
- Dynamische Quellen-Einträge im Seitenmenü (`VideoPlayer.Maui` + `VideoPlayer.Mvu`): Im verbundenen Zustand zeigt das Seitenmenü unter der Sektionsüberschrift „Quellen" je freigegebener Quelle einen eigenen Eintrag mit Name und Quellen-Icon, der direkt in die Titelübersicht der Quelle führt — die bisherige Übersichtsseite „Quellen" entfällt. Während des Ladens erscheint eine Statuszeile, ein leerer Stand wird mit einem Hinweis gekennzeichnet und bei einem Ladefehler zeigt ein sichtbarer Fehlereintrag die Meldung samt Neuversuch. Ohne Serververbindung werden keine Quellen-Einträge angezeigt.
- Vollbreite Kopfbereiche der Detailseiten (`VideoPlayer.Maui` + `VideoPlayer.Mvu` + `VideoPlayer.ApiClient`): Jede Medien-Detailseite (Film, Kollektion, Serie, Staffel, Episode) öffnet jetzt mit einem vollbreiten Kopfbereich nach Web-Vorbild — das Hintergrundbild in Cover-Darstellung unter geschichteten Dunkelgradienten (seitlicher Verlauf, weicher Übergang zum Seitenhintergrund, feine Trennlinie) mit Titel, Metazeile und Handlung unten links, dem Favoriten-Stern oben rechts und den Schaltern „Abspielen"/„Herunterladen" unten rechts. Die Höhe folgt der Fensterbreite (mindestens 360, höchstens 620). Die Bildquelle folgt der Web-Kette — Banner/Fanart/Poster über `api/pictures/{id}`, Episoden über den Still-Endpunkt `api/episodes/{id}/background-image`; auf Serien- und Staffelseiten wechselt der Kopfbereich mit der Staffelwahl auf das Still der ersten Episode. Ohne Bild (fehlende Grafik, Fehlschlag oder Offline) bleibt der Kopfbereich mit Gradienten und Texten stabil.
