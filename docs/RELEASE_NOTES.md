# Release Notes

## Important Notes Before Update

- QR-/ticket-based onboarding requires a server update (`POST api/pairing/bootstrap` plus `POST api/auth/refresh` and `POST api/auth/logout`): onboarding via the pairing QR code / ticket URL / short code from the server admin UI ("Devices" section) requires a VideoPlayer server release that includes the bootstrap endpoint (server issue #231). On a server without the endpoint the pairing code entry shows a clear notice prompting a server update — manual address entry, one-time-code pairing and the sign-in page keep working unchanged as fallbacks.
- Device pairing requires a server update (`POST api/pairing/exchange`): the app now authenticates each device to the server with a device-bound token obtained through a one-time pairing code created in the server admin UI ("Devices" section). This requires a VideoPlayer server release that includes the pairing endpoint (server issue #228). On a server without the endpoint, a new setup only proceeds if a static API token is configured — otherwise the app shows a notice prompting a server update.
- Static API token no longer the primary mechanism, but still configurable as a transition: existing installations with a configured static token (environment variable `VIDEOWEBPLAYER_MAUI_API_TOKEN`, publish property `VideoPlayerApiToken`, token file `client-api-token.txt`) keep working unchanged; pairing is only requested when neither a device token nor a static key is available.

## What's New

- iOS series view fixed — episode list, season order and stable season selection (`VideoPlayer.Maui`, issue #43 step 8): on iOS the series detail page no longer drops its episode list — the virtualized `CollectionView` inside the page's `ScrollView` (which iOS could measure with zero height) was replaced by a `BindableLayout` list following the `MediaCarousel` pattern, with the episode card tap still opening the episode detail page. The season picker now only rebuilds when the season list actually changes and applies `SelectedItem` only on real divergence, and the selection handler ignores echo events that would re-report the already applied model selection — this stops the season order glitch and the snap-back to "Staffel 01" on iOS. Verification boundary: the defect was iOS-specific and no iOS host was available for a runtime check — the cause fixes were verified on Windows (three new end-to-end tests for the series view: visible episode list, ascending season order, season switch that sticks) and the remaining iOS verification is documented.
- Downloads in playlist order for playlist-bound media (`VideoPlayer.Mvu` + `VideoPlayer.Storage`, issue #43 step 7): the automatic download preload now follows the playlist order for Continue Watching entries that carry a playlist reference — instead of enqueueing the next series episodes, the service pages through `api/playlists/{id}/entries/paged` from the current playlist entry and schedules the next preload-count downloadable and accessible entries in the server's playlist order (playlist-bound movies download themselves plus the following playlist entries). The playlist reference (`PlaylistId`/`PlaylistEntryId`/`PlaylistSortOrder`) is persisted on the download manifest via the established column-migration pattern, so existing installs upgrade in place without data loss; entries without a playlist reference keep the series order, and a stale entry reference or an unreachable playlist falls back to the series path. Coverage: new unit tests for the playlist ordering, skipped non-loadable/inaccessible entries, persisted playlist/series hints on the manifest, movie self-plus-next scheduling, both fallback cases and the schema migration (1285 unit tests).
- Playlist administration on the device (`VideoPlayer.Maui` + `VideoPlayer.Mvu` + `VideoPlayer.ApiClient`, issue #43 step 6): playlists can now be managed right in the app — "Neue Playlist" on the overview opens a dialog form (required name with inline validation, description, sort mode), and a new "Verwalten" button on the playlist detail page bundles "Bearbeiten" (name/description), "Playlist löschen" with a confirmation dialog and return to the overview, a sort-mode switch, "Genres bearbeiten" and — for administrators only — "Öffentlich schalten"/"Privat schalten", all through the server administration endpoints. Entry management completes the story: "Zu Playlist" on the media detail page adds the media item to one of your own playlists (with the server's notice for duplicates), and a per-entry context menu removes it or — in manual sort mode — moves it to the beginning, to the end (via max-sort-order + 1) or one position forward/backward, with edge actions hidden. Conflict handling mirrors the server contract: removing an entry tied to Continue Watching asks "Aus Weiterschauen entfernen?" and only the confirmed retry carries `confirmContinueWatchingRemoval=true`, while switching away from manual sort order asks "Sortiermodus ändern?" and retries with `confirmLossOfManualOrder=true` — cancelling either dialog leaves everything untouched. A genre editor lists all server genres as selectable chips preselected from the playlist's genres, with save and reset-to-computed actions; the public/private switch is only offered when the sign-in token carries the `IsAdmin` claim (the server stays authoritative and enforces permissions again), and public playlists owned by other users show no management controls at all. Coverage: new unit tests for every administration endpoint (verb, path, body, confirm flag), service mapping including 409 conflict outcomes, all MVU transitions, plus eleven new end-to-end tests driving the real app through create/edit/delete, add-from-details, entry removal with and without the Continue Watching confirmation, all three move actions, the sort-mode conflict flow, genre set/reset, the admin public switch and the read-only view of a foreign public playlist (1278 unit tests, 50 E2E tests).
- Playlist playback and playlist-aware Continue Watching (`VideoPlayer.Maui` + `VideoPlayer.Mvu` + `VideoPlayer.ApiClient`, issue #43 step 5): playlist entries are now playable — the new "Abspielen" button on the playlist detail page starts playback at the first playable and accessible entry (`POST api/playlists/{id}/play`), and tapping a playable entry starts right at that entry (`entryId`); non-playable entries (shows, seasons, collections, inaccessible media) keep opening the media detail page. During playlist playback the player offers "Zurück"/"Weiter" buttons plus a context line showing the playlist name and position, manual navigation resolves through `play/previous`/`play/next`, and both the end-of-title auto-advance and the error fallback now resolve the next entry through `play/advance` — the ordering always comes from the server, which skips non-playable or inaccessible entries (HTTP 204 ends playback). Continue Watching entries that originated from a playlist carry the playlist reference (`playlistId`/`playlistName`/`playlistEntryId` of the server DTO) through to the home page: tapping them continues playback through the playlist context so the next title follows the playlist order instead of the series order, while entries without a playlist reference keep the existing detail-page-independent series resolution (a media item that is no longer part of the playlist falls back to it as well). The server-supplied `startPositionSeconds` is applied authoritatively, even when the same media exists in another context. Coverage: new unit tests for every MVU transition (start, entry selection, Continue Watching guard with/without reference, navigation guards and exhaustion, auto-advance, error fallback, series-path regression), service tests for the play endpoints (mapping, `entryId`/`currentEntryId` query, 204 handling), mapping tests for the playlist reference and the resume-position override, plus six new end-to-end tests that drive the real app through button start skipping a non-playable entry, entry selection, previous/next navigation, auto-advance, error fallback and a playlist-bound Continue Watching entry that advances by playlist order without a series request (1175 unit tests, 39 E2E tests).
- Playlists overview and detail view (`VideoPlayer.Maui` + `VideoPlayer.Mvu` + `VideoPlayer.ApiClient`, issue #43 step 4): a new "Playlists" menu entry (between Favorites and Downloads) lists the signed-in user's own playlists (`api/playlists`) and all public playlists (`api/playlists/public`) in a single scrollable view with section headers — each card shows the playlist cover (`api/playlists/{id}/cover`, title fallback when none), the sort mode and the display genres. Selecting a playlist pushes a detail page with a cover header (name, description, entry count, sort mode) and its entries in the exact server order, loaded page by page (`api/playlists/{id}/entries/paged`) as the list scrolls; tapping an entry opens its media detail page — playback from playlists is a follow-up step. Playlists are online-only: without a server connection the page shows a clear, retryable error instead of stale cached data. Coverage: new unit tests for endpoint URLs and DTO mapping, service mapping and every MVU transition (offline guard, replace/append paging, stale-answer discard, retry), contract tests for menu/route/page lifecycle, plus four new end-to-end tests that drive the real app through the menu entry with both sections, the detail view in server order, the cover request with fallback, and the error display with a successful retry (1139 unit tests, 33 E2E tests).
- Program log with mail/Share send-off (`VideoPlayer.Maui` + `VideoPlayer.Mvu` + `VideoPlayer.Storage`, issue #43 step 3): the settings page gains a "Protokoll" section — enabling "Protokollierung" writes a timestamped program log to `videoplayer.log` under the profile-scoped `logs` directory (rotates to `videoplayer.previous.log` beyond 1 MiB) and reveals a "Protokoll senden" button that opens a mail draft to `mstromberg84+heimkino@gmail.com` with the log files attached via `Email.ComposeAsync`/`EmailAttachment`; when no mail client can compose a draft (including unpackaged Windows) the Share dialog takes over as fallback, and only when both paths are unavailable does the page show a clear inline notice. The switch takes effect immediately (marker lines are written on enable/disable) and persists across restarts; with logging off no file is written and no send button exists, and all previous `Debug.WriteLine` diagnostics now also flow through `ILogger` into the file log. Coverage: new unit tests for the persistent setting, the switchable file logger (enable/disable markers, rotation, level filter) and the MVU send flow with its disabled-guard, contract tests pinning the XAML wiring, the mail recipient and the DI registrations, plus four new end-to-end tests that drive the real app through disabled/enabled button visibility with log file creation, setting persistence across an app restart, and the send click up to the platform's compose/share boundary (1132 unit tests, 29 E2E tests).
- Context menu on the Continue Watching list (`VideoPlayer.Maui` + `VideoPlayer.Mvu`, issue #43 step 2): holding a Continue Watching entry for two seconds now opens a menu with "Ausblenden" (hide) and "Überspringen" (skip) — matching the server application — while a short tap keeps starting playback directly at the resume position. "Ausblenden" calls `api/continue-watching/hide`, "Überspringen" calls `api/continue-watching/skip`, and the list refreshes itself afterwards via the existing cache-sync path; offline the entry is removed locally from the cached `continue_watching` list. The menu is limited to Continue Watching — Favorites and Recently added are unchanged. Coverage: transition and service unit tests (including the offline cache removal), contract tests pinning the wiring and menu labels, plus three new end-to-end tests that drive the real app through long-press → menu → hide/skip/cancel with the mock server asserting the mutation requests and list refresh (25 E2E tests, 1104 unit tests).
- Direct playback from the Continue Watching list (`VideoPlayer.Maui` + `VideoPlayer.Mvu`, issue #43 step 1): tapping a playable Continue Watching entry (movie or episode) on the home page now starts playback right away at the stored resume position — the detail page is no longer opened in between (and is never loaded in the background). Tapping a show, season or collection entry still opens the detail page, and all other lists (Favorites, Recently added, source overviews, episode lists, collections) keep their existing detail navigation unchanged. For episodes the series context needed for the next-episode feature is loaded independently of the detail page via `api/items/tvshow/{id}` using the context hints of the list entry (offline from the cached show structure), so auto-resume to the next episode keeps working. Coverage: transition and service unit tests plus three new end-to-end tests drive the real app through a direct movie start at the resume position (no detail request on the wire), a direct episode start that resolves the show and advances to the next episode, and a non-playable entry opening details.
- iOS crash on playback start with resume position fixed (`VideoPlayer.Maui`): starting a video with a stored continue-watching position aborted the app on iOS (SIGABRT) because the resume seek reached the native player before it was ready to play — the seek is now only applied once the element reports Playing or Paused and runs under a ten-second timeout. Failed seeks, invalid source addresses and failed source switches are reported as a visible playback error (error panel, episode fallback) instead of crashing the process, and all progress-tick callbacks are fault-isolated so a native-element error can no longer terminate the app. Coverage: two new end-to-end tests drive the real app through playback start at the resume position and a failing stream (visible error instead of process exit).
- Symbolizable iOS crash reports (`scripts/iOS-Deployment.ps1`, CI `package-ios`): release builds now package the `.dSYM` symbol bundles alongside the `.ipa` — the deployment script writes `<name>-dsym.zip` next to the package and the merge workflows upload `release-ios-dsym.zip` to the GitHub release, so future TestFlight/App Store crash reports of a build can be symbolicated; missing dSYMs are a warning, not a failure.
- Developer API moved into reusable libraries (`msTools.DeveloperApi` + `msTools.DeveloperApi.Maui`): the debug-only automation API was extracted from the app into standalone class libraries; item selection via `POST /invoke` now also works on `BindableLayout` lists (tap-gesture invocation, not just CollectionView), and the `/model` snapshot additionally exposes the player state (`playerIsActive`, `playerIsPlaying`, `playerPositionSeconds`, `playerError`) for playback assertions.
- Detail-page header image loads after reconnect (`VideoPlayer.Mvu`): opening a detail page from the offline snapshot used to leave the full-width header without its background image even after the connection returned — only reopening the page showed it. On transitioning to connected state the app now triggers the header load for an already open detail page (same reconnect mechanism as the home-page hero), provided the snapshot names an image source such as an episode still; an already displayed image is not fetched again, and after a failed attempt the next connection retries.
- Page lifecycle leak fixed (`VideoPlayer.Maui`): six pages (Home, Media Details, Downloads, Favorites, Source Overview, Profile) subscribed to the MVU host's `ModelChanged` event in their constructors without ever unsubscribing — closed page instances stayed attached to the host and kept reacting to model changes (memory leak, stale UI updates, potential duplicate reactions). All affected pages now subscribe only while visible — subscribe in `OnAppearing`, unsubscribe in `OnDisappearing`, with guarded update callbacks — following the player/settings page pattern; twelve new contract tests pin the lifecycle.
- QR-/ticket-based onboarding (`VideoPlayer.Maui` + `VideoPlayer.Mvu` + `VideoPlayer.ApiClient` + `VideoPlayer.Storage`): first-run setup now completes in a single step — a new "Mit Kopplungscode verbinden" card on the server setup page accepts the ticket URL from the pairing QR code in the server admin UI ("Devices" section) or the 8-character short code, and on iOS/Android a camera scanner page (ZXing.Net.Maui, camera permission declared per platform, first detection wins) reads the QR code directly. The app splits the ticket URL into server address and opaque ticket, verifies reachability before storing the server, then exchanges the ticket via the public `POST api/pairing/bootstrap` endpoint — same ECDH P-256 / AES-256-GCM handshake as device pairing — for a complete session package: device token, JWT and refresh token land in platform secure storage and the app reaches Home without any sign-in step. Silent renewal now refreshes via `POST api/auth/refresh` first (the rotated refresh token replaces the old one immediately) with the stored-credentials re-login as fallback; signing out revokes the refresh token server-side best-effort via `POST api/auth/logout` and clears all local session secrets. Clear inline errors cover unreadable input, unreachable ticket servers (never persisted), invalid/expired tickets, temporary lockout and servers without the bootstrap endpoint; manual address entry, admin-code pairing and the sign-in page remain available as fallbacks. On Windows there is no camera scan — the manual entry covers it. Coverage: new unit tests for parsing, client, MVU flow, storage, refresh and logout plus six new E2E tests driving the real app through bootstrap → Home, session persistence across restart, refresh rotation, logout revocation, malformed and unreachable input (17 E2E tests, 1013 unit tests, four live-verification screenshots).

Every running step names its phase in text ("Suche läuft …", "Verbindung wird geprüft …", "Kopplung läuft …"). The MVU flow is unchanged — same messages, same route (`serversetup` without a flyout entry), all state still comes from `AppModel`. Coverage: new contract test for the card layout plus a new end-to-end test that drives the real app through connect → health badge → guided pairing card (11/11 E2E tests, 927/927 unit tests).
- Windows end-to-end test suite (`VideoPlayer.E2E.Tests`, xUnit + FlaUI.UIA3): ten tests drive the real `VideoPlayer.Maui.exe` debug build through server setup, device pairing, sign-in and server switching — each test launches its own app process with an isolated `VIDEOPLAYER_PROFILE`, performs real UI-Automation input (text entry, button invoke, flyout navigation; no coordinate clicks) and asserts app state via the Developer API, which gained an `itemIndex` option on `POST /invoke` for coordinate-free CollectionView selection. The backend is a local mock server implementing health, ECDH/AES-GCM pairing exchange, login and the list endpoints, so the suite runs without a server deployment. The static token file is now resolved per profile so isolated profiles no longer inherit the developer's `client-api-token.txt`.
- Developer API for UI automation (`VideoPlayer.Maui` + `VideoPlayer.Mvu`, debug/opt-in only): a local mini HTTP server bound exclusively to `127.0.0.1` on a system-assigned port (written to `devapi.json` next to the executable) exposes four endpoints for automated UI testing — `GET /model` (curated `AppModel` snapshot, no secrets), `GET /tree` (logical element tree with automation ids, visibility, bounds and text, including CollectionView items derived from `ItemsSource` to close the Windows UIA gap), `POST /invoke` (clicked-equivalent per automation id on the UI thread) and `POST /set-text` (entry text incl. `TextChanged`). Release builds never contain the API (`#if DEBUG || DEV_API`, pinned by contract tests).
- Device pairing via one-time code (`VideoPlayer.Maui` + `VideoPlayer.Mvu` + `VideoPlayer.ApiClient` + `VideoPlayer.Storage`): on first start the app pairs the device with the server using a one-time code created in the server admin UI — a new "Pair device" section on the server setup page accepts the code and exchanges it via the public, rate-limited endpoint `POST api/pairing/exchange`. An ephemeral ECDH (P-256) key exchange protects the AES-256-GCM-encrypted device token on the wire; the decrypted token is stored per server address and profile in the platform secure storage (iOS Keychain / Windows Credential Store) — never in Preferences or backups. The app reports the device name during pairing so the device can be identified and revoked in the server admin UI. Clear inline errors cover invalid format, invalid/expired/already-used codes, temporary IP lockout, servers without the pairing endpoint and connection failures. When the server rejects the device token (revoked or expired), the app discards it and returns to the pairing input with a notice — re-pairing happens automatically in the flow. The `X-API-Key` client gate now resolves the stored device token first, ahead of the static sources.
- Watched badge on episodes (`VideoPlayer.Maui` + `VideoPlayer.Mvu`): episode lists on the detail page now mark watched episodes with a round dark badge showing an eye icon in the soft primary color at the top-left of the episode still — matching the web app's watched indicator; unwatched episodes show no badge. The state is driven by the server-supplied `WatchedAt` timestamp, updates immediately when playback marks an episode watched (no page reload) and is carried into offline snapshots (older cached entries count as unwatched).

- New settings management (`VideoPlayer.Storage`): the Settings page now offers automatic downloads, number of episodes to preload, Wi-Fi-only downloads, a download quota in gigabytes (default 5 GB), automatic deletion of watched episodes, auto-resume and the watched time window. All values persist across app restarts and are validated against their allowed ranges.
- Structured local storage with backup separation: backup-relevant data (server list, last connected server, profile data, settings, unsynchronized progress) is kept apart from rebuildable data (offline videos, thumbnails, cached lists, download manifest). On iOS the non-backup locations are excluded via the platform backup attribute, on Windows backup-relevant data goes to the roaming profile directory. Secrets (passwords, tokens) are stored exclusively in platform secure storage and never enter backups; separate profiles via `VIDEOPLAYER_PROFILE` are fully isolated.
- Server management with first-run setup (`VideoPlayer.Storage` + `VideoPlayer.Maui`): on first launch without a configured server a setup dialog offers manual address entry and automatic network discovery (mDNS `_http._tcp.local.` plus UDP broadcast on port 5001). Only servers that pass a live connection check are saved; afterwards the app starts directly with the last connected server. A discreet “Switch server” entry in Settings lists known servers, allows adding new ones and switches the active server without touching any other setting.
- Connection workflow and sign-in (`VideoPlayer.Mvu` + `VideoPlayer.Maui`): on launch the app automatically connects to the last used server and signs in with securely stored credentials, landing in one of four states — connected, sign-in required, server setup required, or offline (when the server is unreachable but local offline data exists). A new sign-in page asks only for username and password (username prefilled), shows inline errors and offers a way back to server selection. Expired tokens are renewed silently via a stored-credentials re-login; only missing or rejected credentials bring up the sign-in page. After a backup restore the app reconnects to the last used server automatically and asks for the password only because secrets are intentionally excluded from backups.
- Network status detection and synchronization: the app detects online/offline transitions at runtime, shows the offline banner without interrupting the current page, and automatically reconnects after network recovery (health check, silent sign-in). A SignalR real-time connection to the server hub `hubs/mediaupdate` refreshes continue-watching, favorites and newly scanned content without manual refresh; if the connection drops permanently it is re-established while online. Playback progress that cannot be delivered is kept in a persistent, backup-covered queue (`pending_progress`) and replayed in chronological order during synchronization — latest position per media, deleted only after successful delivery — surviving app restarts and backup restores.
- Home page with cached media lists (`VideoPlayer.Maui` + `VideoPlayer.Mvu`): the new home page shows three horizontal lists — Continue watching, Favorites and Recently added — as poster cards in the style of the existing app. Lists are loaded from the local cache first, so reopening the app shows content immediately (also offline), and they refresh automatically once fresh server data arrives or a server event (progress, favorites, newly scanned content) updates the corresponding cache. Poster images are loaded via `api/pictures/{id}` and stored in the non-backup preview storage. Tapping an item opens the detail page via the `mediadetails` route carrying the media identity.
- Source browsing and media detail pages: the Sources menu lists the media sources authorized on the server (with icons, a clear offline notice when no connection exists, and retry on failure). Selecting a source opens a browsing page with a horizontal genre bar (including “All”), text search and a poster grid with incremental loading. Detail pages cover movies and episodes (basic details), movie collections (contained movies) and TV shows (season picker with episode lists); episodes and seasons resolve to the show context via embedded references. A favorite star toggles the mark server-side (`api/favorites/toggle`), refreshes the local `cached_favorites` copy authoritatively and updates the home-page favorites list automatically — no silent toggling, consistent after app restart.
- Favorites and Profile pages: the Favorites menu page lists the signed-in server user's favorites as poster cards with title and media type in the style of the web app. Online the server is authoritative — the local `cached_favorites` copy is synchronized first, then displayed; a per-row "Remove" action deletes the favorite server-side (`api/favorites/remove` with the favorite-entry id), refreshes the copy and the home-page favorites list automatically. Offline the cached list stays visible with a clear notice and removal disabled. Tapping a card opens the media detail page with the show/season/episode context. The Profile page shows the signed-in user (username and, when present in the token, e-mail), the active local profile (`VIDEOPLAYER_PROFILE`) and the connected server address; "Sign out" ends the session locally without a server endpoint — tokens and credentials are cleared and the app returns to the sign-in page while server list, settings and offline data are kept.
- Video playback with Picture-in-Picture and progress tracking (`VideoPlayer.Maui` + `VideoPlayer.Mvu` + `CommunityToolkit.Maui.MediaElement` 10.0.0): a dedicated player page (route `player`) plays server streams (`api/items/{type}/{id}/stream` with the access token) or completed downloads from the local manifest — the source abstraction is ready for the upcoming download feature. Playback resumes at the continue-watching position (server list, or the cached copy when offline). Progress is reported every five seconds while playing, marked "watched" within the configured end window and queued losslessly in `pending_progress` when offline for automatic replay after reconnect. With auto-resume enabled the next episode starts automatically near the end (across seasons, in episode order) — never while paused. Source or playback failures show a clear message and fall back to the next episode when available. On Windows a "Mini player" button switches the app window into a compact always-on-top overlay; on iOS the native transport controls provide Picture-in-Picture (background audio is declared in `Info.plist`). Play buttons appear on the detail page for movies and episodes and on each entry of the episode list.
- Download management and automatic downloads (`VideoPlayer.Mvu` + `VideoPlayer.Maui`): media can be downloaded for offline use via a "Download" action on the detail page (movie header and per episode). The "Downloads" menu page lists every job with title, type, state, progress bar and readable errors — usable offline since the inventory lives in the local manifest (`download_manifest`, excluded from backup) — with per-item Cancel, Retry and Delete actions plus the quota usage line. Up to two downloads run in parallel; interrupted jobs restart automatically on connect, after app restart and on network/Wi-Fi recovery (no range resume — the server stream restarts from the beginning). The configured storage quota (default 5 GB) is enforced before and during transfers, including across parallel transfers. "Wi-Fi-only downloads" holds jobs until an unmetered fixed-network connection is present (Wi-Fi or Ethernet). With automatic downloads enabled the app preloads the next episodes of continue-watching entries (count from settings, across seasons via the show context; movie entries download the movie itself), throttled after synchronization, list changes and enabling the setting; completed downloads of watched episodes are optionally removed automatically. Playback prefers the local file and falls back to the server stream when it is missing.
- Full offline operation and backup-restore recovery (`VideoPlayer.Mvu` + `VideoPlayer.Maui` + `VideoPlayer.Storage`): without a server connection the home page keeps working — Continue Watching is built exclusively from completed downloads whose files still exist, missing next episodes appear as dimmed placeholder cards labeled “Not downloaded”, and Favorites/Recently added show the last cached state. Downloads play from the local file; detail pages render offline snapshots that disable server-only actions (favorite toggle, downloads, sources, profile retrieval). After a cloud-backup restore the app reuses the last known server and a stored token or credentials when available; missing secrets lead to a clear re-sign-in notice on the sign-in page with the username prefilled. If the known server is unreachable the app enters offline mode when local data exists, otherwise server setup. On reconnection a full synchronization uploads pending progress and refreshes the home lists. Corrupt cache entries are discarded and re-synchronized; corrupt database files are quarantined as `*.corrupt-*` and rebuilt, with a banner informing the user.

## Wichtige Hinweise vor dem Update

- QR-/Ticket-Onboarding erfordert ein Server-Update (`POST api/pairing/bootstrap` sowie `POST api/auth/refresh` und `POST api/auth/logout`): Das Onboarding über den Kopplungs-QR-Code / die Ticket-Adresse / den Kurzcode aus der Server-Verwaltung (Bereich „Geräte") setzt ein VideoPlayer-Server-Release mit dem Bootstrap-Endpunkt voraus (Server-Issue #231). Auf einem Server ohne diesen Endpunkt zeigt die Kopplungs-Eingabe einen verständlichen Hinweis auf das Server-Update — Adresseingabe, Einmal-Code-Pairing und Anmeldemaske funktionieren unverändert als Fallback weiter.
- Geräte-Pairing erfordert ein Server-Update (`POST api/pairing/exchange`): Die App authentifiziert jedes Gerät jetzt mit einem gerätegebundenen Token, das über einen Einmal-Pairing-Code aus der Server-Verwaltung (Bereich „Geräte") bezogen wird. Voraussetzung ist ein VideoPlayer-Server-Release mit dem Pairing-Endpunkt (Server-Issue #228). Auf einem Server ohne diesen Endpunkt gelingt eine Neueinrichtung nur mit einem konfigurierten statischen API-Token — andernfalls zeigt die App einen Hinweis mit der Aufforderung zum Server-Update.
- Statischer API-Token nicht mehr der primäre Mechanismus, aber weiter als Übergangslösung konfigurierbar: Bestehende Installationen mit hinterlegtem statischem Token (Umgebungsvariable `VIDEOWEBPLAYER_MAUI_API_TOKEN`, Publish-Eigenschaft `VideoPlayerApiToken`, Token-Datei `client-api-token.txt`) funktionieren unverändert weiter; das Pairing wird nur eingefordert, wenn weder ein Geräte-Token noch ein statischer Schlüssel vorhanden ist.

Eine neue Anmeldemaske fragt nur Benutzername und Passwort ab (Benutzername vorbefüllt), zeigt Inline-Fehler und bietet den Weg zurück zur Serverauswahl. Abgelaufene Anmelde-Tokens werden im Hintergrund über eine erneute Anmeldung mit den gespeicherten Zugangsdaten erneuert; nur fehlende oder abgelehnte Zugangsdaten führen zur Anmeldemaske. Nach einer Backup-Wiederherstellung verbindet sich die App automatisch mit dem letzten Server — die erneute Passwortabfrage erfolgt nur, weil Geheimnisse bewusst nicht ins Backup gelangen.
- Netzwerkstatus-Erkennung und Synchronisation: Die App erkennt Online↔Offline-Wechsel zur Laufzeit, zeigt den Offline-Hinweis ohne die aktuelle Seite zu verlassen und stellt die Verbindung nach Netzwerk-Wiederkehr automatisch wieder her (Erreichbarkeitsprüfung, stille Anmeldung). Eine SignalR-Echtzeit-Verbindung zum Server-Hub `hubs/mediaupdate` aktualisiert Weiterschauen, Favoriten und neu eingescannte Inhalte ohne manuelle Aktualisierung; bei endgültigem Verbindungsverlust wird sie im Online-Zustand neu aufgebaut. Nicht zustellbare Wiedergabefortschritte landen in einer persistenten, backup-pflichtigen Warteschlange (`pending_progress`) und werden bei der Synchronisation in chronologischer Reihenfolge nachgesendet — je Medium nur der neueste Stand, gelöscht erst nach erfolgreicher Übertragung — und überstehen App-Neustarts und Backup-Wiederherstellungen.
- Startseite mit gecachten Medienlisten (`VideoPlayer.Maui` + `VideoPlayer.Mvu`): Die neue Startseite zeigt drei horizontale Listen — „Weiterschauen", „Favoriten" und „Neu im Programm" — als Poster-Karten im Stil der bisherigen App. Die Listen werden zuerst aus dem lokalen Cache geladen, sodass beim erneuten Öffnen sofort Inhalte sichtbar sind (auch offline); sobald aktuelle Serverdaten vorliegen oder ein Server-Ereignis (Fortschritt, Favoriten, neu eingescannte Inhalte) den zugehörigen Cache aktualisiert, frischen sich die Listen automatisch auf. Vorschaubilder kommen über `api/pictures/{id}` und liegen in der nicht backup-pflichtigen Vorschau-Ablage. - Favoriten- und Profil-Seite: Die Menüseite „Favoriten" zeigt die Favoriten des am Server angemeldeten Benutzers als Poster-Karten mit Titel und Medientyp im Stil der Webanwendung. Online bleibt der Server führend — die lokale Kopie `cached_favorites` wird zuerst synchronisiert und dann angezeigt; die Aktion „Entfernen" je Eintrag löscht den Favoriten serverseitig (`api/favorites/remove` mit der Favoriten-Eintrags-ID), erneuert die Kopie und die Startseiten-Favoriten folgen automatisch. Offline bleibt die gespeicherte Liste mit klarem Hinweis sichtbar und das Entfernen ist gesperrt. Ein Tap auf eine Karte öffnet die Detailseite des Mediums mit dem Serienkontext (Staffel/Episode). Die Wiedergabe setzt am gemerkten Weiterschauen-Stand fort (Serverliste, offline aus der Cache-Kopie). Der Fortschritt wird im Fünf-Sekunden-Takt gemeldet, innerhalb des eingestellten Endfensters als „angesehen" markiert und offline verlustfrei in `pending_progress` vorgehalten — bei Online-Rückkehr wird automatisch nachgesendet. Bei aktivierter Auto-Fortsetzung startet gegen Ende automatisch die nächste Episode (staffelübergreifend, in Episodenreihenfolge) — nie im Pausenzustand. Bis zu zwei Downloads laufen parallel; unterbrochene Aufträge werden beim Verbindungsaufbau, nach App-Neustart und bei Netzwerk-/WLAN-Rückkehr automatisch neu gestartet (kein Range-Resume, der Server-Stream beginnt erneut).
